# 部署方案

> 2026-10-03 · 用户要求「可以部署在 GitHub 上，然后连接到 Cloudflare」

## 结论先说

**现在不能直接部署到 Cloudflare。** 不是配置问题，是架构问题。

写作台是本地 Node 服务，有三个硬依赖 Cloudflare 都提供不了：

| 依赖 | 现状 | Cloudflare Pages | Cloudflare Workers |
|---|---|---|---|
| 本地文件系统 | `data/*.json` 直接 `writeFileSync` 到磁盘 | ❌ 纯静态托管 | ❌ Workers 无 FS |
| Node 运行时 | `server.mjs` 跑在 `node:http` 上 | ❌ 无 | ❌ V8 isolate，模块 API 不同 |
| 出站抓取 | 热点榜实时访问源站 | ❌ | ⚠️ 有配额，且源站多数反爬 |

GitHub Pages 同理 —— 只能放静态文件，而这个项目的界面是 `index.html` + `app.js` + `app.css`
加一个必须同源运行的 API。

**把仓库同步到 GitHub 当代码备份，现在就能做**，已配好 `.gitignore`。

---

## 三条路线

### 路线 A · 只做 GitHub 备份（10 分钟，现在可做）

仓库推上去，代码有版本、有备份、能协作。

不做的话：某天硬盘出问题，六轮的工作全没。

代价：无。数据（`data/`）默认入库，因为它们是项目的一部分。
不想上传稿件的话，取消 `.gitignore` 里那三行的注释。

---

### 路线 B · 前端上 Cloudflare Pages，后端留本地（半天）

把 `index.html` / `app.js` / `app.css` 部署成静态站，
`api()` 改成指向本地 `http://127.0.0.1:8848`。

**问题是这解决不了任何需求** —— 前端在公网，后端在你电脑上，
别人打开那个网址只会看到一个连不上的空壳。而且要处理 CORS，
本地服务现在没放开跨域。

唯一有意义的场景：你自己在别的机器上访问，界面走公网、数据走本地。
这种情况用 Tailscale / frp 更直接，不需要改代码。

**不推荐。**

---

### 路线 C · 全量搬到 Cloudflare Workers + D1（约两周）

这是唯一能让它真正公网可用的路子。

要做的：

1. **存储层替换**
   `data/*.json` → D1（SQLite）或 KV。
   写一个存储适配层，让业务代码不直接碰 `fs`。

2. **运行时替换**
   `node:http` → Workers 的 `fetch` handler。
   `server.mjs` 的路由表可以照搬，但要逐个改 API 形态。

3. **markdown-it 换掉**
   Workers 跑不了这个 npm 包（依赖 Node 内置模块）。
   要么换成纯 JS 的 markdown 解析器，要么自己写一个够用的。

4. **出站抓取改造**
   热点榜抓取要处理 CORS、Workers 配额、超时。
   源站反爬只能靠 Cloudflare 的出站 IP 池，比本地更受限。

5. **图片存储**
   `data/images/` → R2。走签名 URL。

6. **成本**
   Workers 免费额度是每天 10 万次请求。抓取热点很吃配额，
   重度使用大概率要付费。

**做完之后**：一个公网可访问的写作台。但要接受几个现实约束 ——
抓取成功率会下降（反爬）、速度受 Worker 冷启动影响（首次请求慢）、
数据在云端（隐私考虑）。

---

## 我的建议

**先做路线 A。** 它零风险、十分钟能完成，解决「代码会丢」这个真实问题。

路线 C 是一次架构重写，不是部署配置。它值得做，但应该当成一个独立项目来排期，
而不是顺手挂在某次改 UI 的尾巴上。而且要先想清楚一件事：

**这个工具的使用场景是「本机写稿，数据不出门」。**
把它放到公网上，等于稿子、事实清单、素材全在云端。
对个人写作工具来说，这未必是想要的变化。

如果确实需要多设备访问，我建议的顺序是：

1. 路线 A（GitHub 备份）
2. 先用 Tailscale 打通手机和电脑 —— 十分钟，不改一行代码
3. 真觉得 Tailscale 不够用，再评估路线 C
